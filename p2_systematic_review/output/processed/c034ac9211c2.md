## Abstract summary
The paper presents a model-to-text generation technique implemented in EGL that produces integrated Python and Qiskit code from extended UML models for hybrid classical-quantum systems. The approach generates quantum circuits from activity diagrams and classical code from class diagrams, linking them when classes are stereotyped as quantum drivers, and is preliminarily validated with a financial web application example to support forward engineering in software modernization for hybrid systems.
## Methodology
The paper proposes a model-to-text generation technique implemented as two sequential EGL (Epsilon Generation Language) transformations that convert extended UML designs for hybrid classical-quantum systems into integrated Python (classical) and Qiskit (quantum) source code. Inputs are UML class diagrams and UML activity diagrams extended by a Quantum UML profile (stereotypes such as <<QuantumGate>>, <<Measure>>, <<QuantumDriver>>, <<Quantum>> and Lanes representing qubits). Step 1: activity-diagram -> Qiskit .py generation: create QuantumRegister objects (one per Lane), create ClassicalRegister objects for qubits affected by measure actions, instantiate a QuantumCircuit with the appropriate registers, add quantum gates in preserved order, and map controlled gates using modelled SendSignalAction/AcceptEventAction pairs across Lanes; persist one Python file per activity. Step 2: class-diagram -> Python generation: map packages to directory structure, map classes to Python files, translate UML attributes and types to Python attributes (including generating getters/setters), create method signatures from UML operations (left empty for developers), and detect integration points where a UML class stereotyped <<Quantum Driver>> depends on a <<Quantum>> class whose name matches a previously generated quantum .py file; inject a QuantumCircuit attribute referencing the generated quantum circuit into the driver class. The transformations are implemented in EGL templates, can be executed from Papyrus (Eclipse) or via a JavaFX tool developed by the authors, and were preliminarily validated by generating code for a small financial web application (a European call option pricing example inspired by the Qiskit finance library). Generated artifacts were compared to a manually developed implementation: classical code was produced as skeletons, and generated quantum circuits were functionally equivalent in practice (minor gate-order differences that did not affect results). The authors publish the EGL templates and generated models/code in a public repository for reference.
**Frameworks:** Qiskit, EGL (Epsilon Generation Language), UML (with Quantum UML profile), Papyrus (Eclipse), JavaFX, Python, Qiskit Finance (inspiration/example)

## Limitations
- The generative technique is preliminary and has been validated only in a limited, preliminary way (single small financial web application example).
- Generated classical code provides only skeletons (empty operation bodies) that must be manually completed by developers.
- The transformation currently supports only UML class diagrams and UML activity diagrams (other UML diagram types are not used as inputs).
- The implementation targets only Python and Qiskit; other programming languages and quantum frameworks are not supported.
- The transformation does not consider predefined quantum software libraries and other advanced Python/Qiskit elements (e.g., higher-level Qiskit modules) by default.
- The generated quantum code can differ in the order of gate application compared to hand-written code (although differences reported did not affect results in the example).
- Mapping from UML data types to Python types is required and must be parameterized/configured (the mapping choice is not standardized by the technique).
- The EGL transformation and toolchain have not been validated with multiple heterogeneous UML models or larger, real-world hybrid systems; generalizability is unproven.
- [inferred] The integration mechanism depends on specific UML stereotypes and name-matching (e.g., <<Quantum Driver>> and <<Quantum>> classes), making the approach fragile to modeling variations.
- [inferred] No formal verification or automated correctness proofs are provided to ensure that generated quantum circuits are semantically equivalent to intended designs beyond ad-hoc testing.
- [inferred] Scalability and performance of the transformation (for large models or many circuits) have not been evaluated.
- [inferred] The approach is tied to the authors' UML profile and may require adaptation to other profiles/DSMLs; portability/interoperability is unclear.
- [inferred] The transformation focuses on code skeleton generation and does not address deployment, orchestration, or runtime integration with quantum backends and services.
- [inferred] Handling of complex quantum constructs (e.g., sophisticated controlled operations, parametrized gates, noise models, or hybrid quantum-classical control flows) may be limited or untested.
## Open questions
- How well does the technique scale to larger, industrial-scale hybrid systems with many classes and circuits?
- How can we guarantee semantic equivalence (functional correctness) of generated quantum code when gate order differs from manual implementations?
- What is the best way to include and map predefined quantum libraries and higher-level Qiskit constructs into the generation process?
- How should UML-to-Python type mappings be standardized or configured to reduce ambiguity and developer effort?
- Can the approach be extended to generate code for other quantum frameworks and classical languages (e.g., Cirq, PyQuil, C++, Java)?
- How resilient is the integration approach to variations in modeling practices (e.g., different stereotype names, package structures, naming mismatches)?
- What validation and testing regimes are required to build confidence in generated hybrid systems (unit tests, property-based tests, formal verification)?
- How can the transformation be integrated into real-world development workflows, CI/CD pipelines, and toolchains used by industry?
- How should hybrid control flows (interleaving classical and quantum computation, adaptive circuits) be modeled in UML and generated into executable code?
- What additional UML diagrams or modeling constructs (e.g., sequence, deployment, state machines) would be useful to support richer generation and deployment artifacts?
- How to handle runtime concerns such as connecting to remote quantum backends, error mitigation, and performance tuning from models?
- How to support preservation of developer-introduced deviations from UML models (round-trip engineering) and evolve models and code coherently?
