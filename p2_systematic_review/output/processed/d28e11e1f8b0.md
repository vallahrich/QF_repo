## Abstract summary
The paper proposes a standard-ready testing pipeline for quantum computing applications within a quantum software engineering lifecycle, focused on the TEST phase from code testing to release. It addresses NISQ-era challenges by detailing processes for quantum-classical code debugging, backend selection and resource estimation, noisy validation, and fallback strategies like problem splitting and circuit cutting to enable practical experimentation and continuous delivery.
## Methodology
This paper is conceptual and proposes a standard-ready, multi-stage testing pipeline for gate-based quantum computing applications in a software engineering lifecycle. The pipeline is organized into sequential activities: (1) Code testing & debugging: introduce unit-testing concepts and specialized assertions for quantum code (AssertProbabilityEquality, AssertExpectationValueEquality, AssertUnitaryEquality, AssertStatevectorEquality, AssertDistributionStability), encourage use of classical simulators for correctness checks (with caveats on scalability), and provide a Python-style decorator example for injecting pre-configured noisy backends into tests. (2) Backend decision: a two-stage backend filtering process — first filter candidate backends by user account access, feature compatibility (e.g., dynamic circuits, native gates), and circuit width; second, transpile to remaining backends and perform resource estimation using a circuit cost metric (example: C = −D log K − Σ log F1q − Σ log F2q), analysis of active-qubit time vs. coherence times, and application-centric benchmark metrics to select best backend(s). (3) Validation: run noisy simulations (device-specific and generic noise models) of transpiled circuits to predict performance and guide further optimization or backend selection. (4) Redesign / Problem splitting / Quantum circuit cutting: when backends or validations fail, propose redesign, divide-and-conquer problem splitting, or circuit-cutting methods (e.g., CutQC, randomized-measurement cutting) and optionally apply quantum error mitigation techniques; note exponential overheads and sampling penalties. (5) Execution on noisy QPU: after passing validation, execute on real hardware and collect metrics such as reliability, reproducibility and runtime to inform further iterations. The methodology emphasizes iterative evaluation, pragmatic use of classical simulation for small sizes, a set of structured quantum-specific unit assertions, a two-stage backend selection with cost modeling and timing vs. coherence analysis, and fallback strategies including circuit cutting and problem splitting. The paper does not present empirical experiments or datasets but outlines where and how simulations and hardware runs would be integrated into the pipeline and indicates plans to implement a Python testing framework in future work.

## Limitations
- State monitoring is fundamentally limited: quantum states cannot be non-destructively monitored or cloned, preventing traditional runtime inspection and complicating debugging and fault localization.
- Classical simulation reliance is limited by exponential resource costs — simulators can only be used for small problem sizes or classically simulatable circuits, reducing ability to test and verify large instances.
- Verification for problem sizes beyond classical simulation is challenging; there is no general practical method to certify correctness of outputs for large, classically intractable instances on NISQ devices.
- Noisy (device-specific) simulators often produce optimistic results that do not match real QPU outputs, limiting the predictive power of noisy simulations for validation.
- Unit testing support is inconsistent across toolchains: Q# provides unit testing features whereas most Python-based quantum frameworks lack integrated, language-native unit-testing/debugging facilities.
- Backend decision and resource estimation rely on heuristics and rough cost metrics (e.g., factorized gate-fidelity assumptions, phenomenological penalty factors) that do not capture all noise sources (e.g., crosstalk) and therefore provide only approximate guidance.
- Access to detailed backend calibration/error metrics may be restricted by cloud provider policies or paid tiers, limiting the information available for backend selection and accurate estimation.
- Quantum circuit cutting and problem-splitting approaches incur substantial computational and sampling overheads (exponential scaling with number of cuts), making them a costly and less efficient fallback.
- Effective quantum error correction is not available for useful circuit sizes on current NISQ devices, so mid-circuit error-corrective strategies cannot be relied upon for debugging or correctness.
- The testing pipeline cannot guarantee with full confidence that a chosen backend and transpilation will yield acceptable output quality on real hardware; successful backend decision and validation remain probabilistic.
- Post-cut reconstruction of global circuit outputs from subcircuit results requires non-trivial classical post-processing and introduces additional complexity and potential sources of error.
## Open questions
- How can one verify correctness of quantum application outputs for problem instances that are infeasible to classically simulate?
- What practical and scalable verification protocols are available or can be developed for NISQ-era devices to provide stronger guarantees about result correctness?
- How can noise models and device simulators be improved to better match real hardware behaviour (including non-factorizable errors like crosstalk) so validation more accurately predicts QPU outcomes?
- What is the best design for a general-purpose, easy-to-use unit testing and assertion framework for Python-based quantum development that captures quantum-specific testing needs?
- How can backend selection and resource-estimation metrics be made more reliable and robust to changing device calibrations and incomplete provider metrics?
- How can the computational and sampling overheads of quantum circuit cutting and problem-splitting be reduced, or otherwise made practical, for larger real-world problems?
- How to integrate circuit cutting, problem splitting and quantum error mitigation into an automated CI/CD-style testing pipeline without prohibitive cost?
- Can runtime assertions or limited (non-destructive) state checks be implemented practically on NISQ hardware to aid debugging, and if so, how to do this given hardware limitations?
- How to quantify and convey uncertainty/confidence in pipeline decisions (backend choice, validation outcomes) to software developers and stakeholders?
- What benchmarks and application-centric performance predictors best inform backend decision for hybrid quantum-classical workflows?
