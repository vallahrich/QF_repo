## Abstract summary
The paper empirically analyzes 985 Jupyter Notebooks from 80 open-source projects to identify how quantum software patterns are applied in practice. The authors build a knowledge base by mapping components from Qiskit, PennyLane, and Classiq to an existing pattern atlas, introduce nine new patterns, and develop a semantic search tool to detect pattern usage, finding a layered adoption from low-level circuit utilities to algorithmic primitives and domain-specific application patterns.
## Methodology
The authors performed a large-scale empirical mining study of quantum software patterns in Python-based open-source projects. The method consisted of four main stages: (1) identify framework-specific high-level quantum components by programmatically parsing the source code and public APIs of three representative frameworks (Classiq SDK v0.88.0, PennyLane v0.44.0, Qiskit v2.3.0). Extraction scripts collected component fully-qualified names and docstrings (exported as CSVs) and a de-duplication / clustering step (using sentence-transformer embeddings) was applied for Qiskit. (2) Manually match and consolidate the extracted components against a master pattern list (the Quantum Computing Patterns Atlas). Three authors independently classified concepts to patterns, discussed disagreements, and defined new patterns where concepts did not match existing ones, resulting in an extended catalog (61 patterns total, 9 newly defined patterns and some unifications). (3) retrieve target repositories via the GitHub API using topic-based queries (topic: quantum-computing, quantum-machine-learning, quantum-algorithms, language:Python), sort by stars, and filter by heuristics (>=30 stars, >=10 contributors, active maintenance within 12 months, exclude books/tutorials); final dataset comprised 80 projects (including a Cirq monorepo) and 985 Jupyter notebooks. (4) semantic pattern matching across target code: notebooks were converted to .py files, a knowledge base of reference concept embeddings was created (two embedding sets per concept: name embeddings and docstring/summary embeddings) using the sentence-transformers all-mpnet-base-v2 model run locally; target scripts were parsed with Python AST to extract function/method calls and comments; embeddings were computed for call names and consolidated comment blocks and compared to the knowledge base via cosine similarity. Two match types and thresholds were used: name matches (call name vs. concept-name embeddings) with threshold 0.95 and summary matches (comments block vs. docstring embeddings) with threshold 0.7. Matches were recorded with metadata (file path, matched concept, pattern, match type, triggering text, similarity score) and aggregated to produce statistics (pattern prevalence, source/adoption analysis, gap analysis). The authors tuned thresholds experimentally, used high thresholds to reduce false positives, and produced a CSV of matches and a final report. The process also included manual consolidation steps (mapping matched concepts to high-level patterns).

**Algorithms used:** Quantum Fourier Transform (QFT), Quantum Phase Estimation (QPE), QAOA, VQE, VQA, Quantum Neural Network (QNN), Grover (Amplitude Amplification / Grover operator), Quantum Amplitude Estimation (QAE), Hamiltonian Simulation (e.g., Suzuki-Trotter), Quantum Singular Value Transformation (QSVT), Quantum Monte Carlo (as a detected domain component)
**Frameworks:** Qiskit, PennyLane, Classiq SDK, Cirq

## Findings

- [supported] We built a knowledge base of reusable quantum components by extracting documented components from three frameworks: Qiskit, PennyLane, and Classiq SDK.
- [supported] Using manual mapping against the Quantum Computing Patterns Atlas and framework code, we extended/refined the pattern catalog and documented new pattern categories (reported in the paper as nine new patterns overall).
- [supported] We developed a reusable semantic search tool (based on the all-mpnet-base-v2 sentence-transformer embeddings) to detect framework concepts and associated patterns in target project code and comments.
- [supported] From the extended catalog (61 patterns), only a subset were implemented in the investigated frameworks (paper reports 24–25 patterns found in frameworks) and most of those appeared in practitioner notebooks (22 patterns observed in notebooks).
- [supported] We detected 573 semantic matches for QC concepts across 251 unique files, corresponding to 117 distinct concepts from our knowledge base.
- [supported] Name-level matches (matching code call names to concept names) accounted for 384 matches with a very high average similarity (≈0.99), indicating direct use of library components; summary/comment-level matches produced 189 matches with average similarity ≈0.70, indicating topical discussion or explanation.
- [supported] Developers use quantum patterns at three abstraction layers in practice: foundational circuit utilities (fine-grained control), algorithmic primitives (e.g., QFT, QPE, amplitude amplification), and domain-specific application components (optimization, finance).
- [supported] The most frequently matched patterns in notebooks included Basis Change, Quantum Phase Estimation (QPE), Domain Specific Application, Quantum Arithmetic, and Circuit Construction Utility (counts reported in the paper).
- [supported] Classiq-origin components were prominent among top matched concepts in practitioner notebooks (Classiq accounted for many of the top-detected concept instances).
- [supported] Two patterns present in frameworks were not detected in any examined notebooks: Function Table and Schmidt Decomposition.
- [speculative] The observed layered adoption and prevalence of higher-level primitives suggest a maturing ecosystem where developers increasingly prefer high-level building blocks over low-level gate-by-gate construction.
- [speculative] The absence of some framework-provided patterns in notebooks may indicate a gap between library-provided patterns and practitioner needs or adoption priorities.
- [supported] Frameworks show domain and API specialization: PennyLane is prominent in QML-related components; Qiskit emphasizes gate-level and circuit utilities; Classiq emphasizes high-level functional components.

**Results summary:** This study built a knowledge base from Qiskit, PennyLane, and Classiq SDK components, extended the quantum pattern catalog, and used a sentence-transformer based semantic search tool to mine 985 Jupyter Notebooks from 80 open-source projects. The search yielded 573 matches across 251 files corresponding to 117 concepts. Only a subset of cataloged patterns are implemented in frameworks and even fewer are used in practitioner notebooks; 22 of the identified framework patterns appear in notebooks. ## Limitations
- Knowledge base derived from only three frameworks (Qiskit, PennyLane, and Classiq), which is not exhaustive and may miss concepts present in other frameworks
- Manual categorization of quantum concepts into patterns (performed independently by three authors), introducing risk of human bias despite consensus discussions
- High similarity thresholds in the semantic search (0.95 for name matches, 0.7 for summary matches) were used to reduce false positives but may have missed less common or more loosely expressed pattern instances
- Analysis restricted to Python-based projects and specifically to Jupyter Notebooks, limiting applicability to code written in other languages or to non-notebook codebases
- Dependence on docstrings and comments: the methodology leverages documentation to create and match concepts, so poor or missing documentation reduces detectability and biases results toward well-documented frameworks
- [inferred] Use of a single embedding model (all-mpnet-base-v2) and a local, deterministic embedding approach may limit the ability to capture deeper or alternative code/document semantics compared to other models or multimodal approaches
- [inferred] Project selection filters (minimum stars, minimum contributors, recent activity, exclusion of tutorials/books) bias the dataset toward popular and active repositories and may exclude relevant legacy, niche, or educational code
- [inferred] Converting Jupyter Notebooks to plain Python scripts for analysis may lose notebook-specific context (cell structure, inline narrative, outputs) that could affect pattern-detection in practice
- [inferred] Some frameworks (e.g., Cirq) were not used as source frameworks in the knowledge-base construction because they lack a centralized library of high-level abstractions; this choice might omit design idioms present in those ecosystems
- [inferred] Pattern detection is limited by the contents of the knowledge base; patterns not present or represented in the base cannot be found in the target repositories
## Open questions
- Why do many patterns documented in the catalog not materialize in open-source practitioner code?
- Why were specific patterns (e.g., Function Table and Schmidt Decomposition) present in frameworks but not detected in any target projects?
- How can pattern categorization be automated reliably (e.g., via embedding models or LLMs) while maintaining accuracy and interpretability?
- How does pattern usage and prevalence differ across other quantum programming languages (Q#, Julia, C++, etc.) and ecosystems?
- How can the semantic search be improved (or thresholds tuned) to discover more relevant matches without substantially increasing false positives?
- How resilient is pattern detection in the presence of poor or absent documentation, and what methods can improve detection in such cases?
- How do hardware limitations, noise characteristics, and available devices influence the adoption of particular patterns or abstraction layers in practice?
- How do pattern usages differ between educational/tutorial notebooks (demonstrations) and production or industry-grade quantum software?
- To what extent do high-level abstractions (as provided by frameworks) lower the barrier for non-physicist practitioners, and how does this affect correctness, performance, and reproducibility?
- What is the best way to represent task-level QML constructs (e.g., classification, QNNs) versus architectural design patterns, and should some task-level constructs be reclassified?

**Future work:**
- Expand the analysis beyond Python to other quantum programming languages such as Q# and Julia
- Develop an automated tool for pattern categorization, potentially using embedding models or large language models (LLMs)
- Fine-tune the semantic search component to lower similarity thresholds and increase recall while keeping false positives low
