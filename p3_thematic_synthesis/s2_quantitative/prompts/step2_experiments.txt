## Task

## Extract Per Experiment

### Algorithm
- **family**: MUST be exactly one of this closed set — do NOT invent new values: qaoa, vqe, amplitude-estimation, quantum-ml, quantum-walk, hhl, hybrid, grover, quantum-svm, quantum-simulation, classical-simulation, other-gate-based, other. `quantum-annealing` and `qubo` are NOT valid values (annealer papers are out of scope; QUBO formulations on gate-based hardware use `qaoa` or `grover`). Do NOT use Phase-2 taxonomy codes (e.g., "variational-nisq", "error-mitigation", "quantum-cryptography", "qft-phase-estimation") — map them: QAOA → qaoa; VQE/variational → vqe; QPE/QFT applications → amplitude-estimation; Shor/QKD → other-gate-based; error mitigation studies without a distinct quantum algorithm → other.
- **variant**: specific variant name (e.g., "QAOA with warm-start", "hardware-efficient VQE")
- **ansatz**: circuit ansatz if applicable (e.g., "RealAmplitudes", "EfficientSU2", "UCCSD")
- **optimizer**: classical optimizer (e.g., "COBYLA", "SPSA", "Adam", "L-BFGS-B")
- **num_layers**: QAOA depth p, VQE layers, ansatz repetitions
- **convergence_criteria**: stopping condition (e.g., "max 1000 iterations", "gradient < 1e-6")
- **hyperparameters**: ALL reported parameters as key-value pairs
- **parameter_initialization**: how initial parameters are set (e.g., "random uniform [0, 2π]", "warm-start from classical solution", "TQA schedule")
- **optimizer_settings**: max_iterations, tolerance, step_size, learning_rate_schedule, parameter_bounds if reported

### Problem Formulation
- **encoding_method**: amplitude_encoding, angle_encoding, basis_encoding, QUBO, block_encoding, qRAM. A QUBO/Ising problem encoding is in scope only when the solver is gate-based (QAOA, Grover, amplitude-estimation, etc.).
- **encoding_details**: how variables map to qubits (e.g., "9-bit discretization per asset", "1 qubit per binary variable", "log2(N) qubits for N assets")
- **objective_function**: mathematical formulation
- **constraints_handling**: penalty terms, XY-mixer, feasibility filter, post-selection
- **num_binary_variables**: number of binary variables in QUBO/Ising
- **problem_hamiltonian**: Hamiltonian form if specified
- **num_ancilla_qubits**: ancilla qubits required (if reported separately)

### Problem Instance
- **description**, **num_assets**, **time_steps**, **num_features**, **dataset_size**
- **data_type**: synthetic, real_market, proprietary, public_benchmark
- **dataset_name**, **dataset_specification**: ticker_symbols, date_range, benchmark_name, preprocessing, train_test_split
- **data_preprocessing_details**: exact steps to prepare input data (e.g., "log returns, 252-day annualization, Shapiro test for normality, remove assets with negative expected return")
- **evaluation_methodology**: how results are evaluated (e.g., "10-fold CV", "20 independent runs per config", "average over 100 random seeds")

### Quantum Resources — CRITICAL: You MUST extract these for every experiment
Search carefully — these often appear in tables, figures, circuit diagrams, setup sections, or appendix. For QAOA/Grover-on-QUBO problems on gate-based hardware, record the number of binary variables in `num_binary_variables` (problem-formulation block), and report `num_qubits` as the actual qubit register size of the gate-based circuit.
- **num_qubits**: Total qubits used. Search for "qubit", "q =", "n =", register sizes, binary variables.
- **qubit_type**: logical, physical, or not_specified
- **circuit_depth**: Total depth. Search for "depth", "layers", "p =".
- **circuit_depth_transpiled**: Depth after transpilation.
- **gate_count_total**, **cnot_count**, **two_qubit_gate_count**, **t_count**, **t_depth**
  - `two_qubit_gate_count` is the TOTAL two-qubit entangling gate count (CNOT + CZ + iSWAP + ECR + any native 2q gate). If the paper only reports CNOTs, set both `cnot_count` and `two_qubit_gate_count` to that number. If the paper reports only a generic "2-qubit gate count" or "entangling gate count", put it in `two_qubit_gate_count` and leave `cnot_count` null.
- **num_shots**: Search for "shots", "repetitions", "samples", "measurements".
- **num_variational_params**: Number of trainable parameters.
- **gate_fidelity**: Single-qubit or two-qubit gate fidelity if reported (e.g., 99.5%, 0.995).
- **readout_fidelity**: Measurement/readout fidelity if reported.
- **error_correction**: code_type, code_distance, physical_qubits_per_logical, total_physical_qubits, logical_error_rate, physical_error_rate_assumed

### Hardware — CRITICAL: You MUST identify the hardware for every experiment
- **type**: simulator_statevector, simulator_noisy, simulator_other, real_qpu_superconducting, real_qpu_trapped_ion, real_qpu_photonic, real_qpu_neutral_atom, not_specified. `quantum_annealer` is NOT a valid value — annealer experiments are out of scope.

- **framework**: Qiskit, PennyLane, Cirq, Q#, Braket, etc. Ocean/QBSolv are annealer-stack tools and out of scope.

### Noise & Implementation

### Complexity Analysis (for Hoefler assessment — search Introduction, Related Work, Discussion)

## Rules
- Classical-only methods are BASELINES, not experiments.
- **Classical solvers are NEVER separate quantum experiments**, even when they appear in a quantum paper's experimental section. The following artefacts are ALWAYS classical: QBSolv (classical decomposer), simulated annealing, tabu search, CPLEX, Gurobi, SCIP, MOEA/D, NSGA-II, classical SVM, random forest, logistic regression, gradient boosting, classical neural networks, Monte Carlo (when run on CPU/GPU only). Record them under `classical_baselines` of the paper's gate-based experiment, never as their own `experiments[]` entry. If the paper's ONLY solver is in this list, return `{{"experiments": [], "out_of_scope": true, "out_of_scope_reason": "no gate-based quantum experiment — only classical solver(s)"}}`.
- If the same algorithm is tested at multiple problem sizes, it is ONE experiment with scalability data.
- Extract ALL reported hyperparameters.
- If the paper has more than 5 experiments, focus on the 5 most distinct/important ones.
- Search the ENTIRE paper for resource data: methods, setup, results, appendix, figure captions.
- For QAOA/Grover-on-QUBO problems on gate-based hardware, set `algorithm.family` to `qaoa` or `grover` and record the binary-variable count in `problem_formulation.num_binary_variables`. Do NOT use `qubo` or `quantum-annealing` as algorithm families.
- Use null for fields not reported. Never fabricate values.
- **Provenance tracking is mandatory.** For every experiment, populate the "provenance" object:
  - "paper_reported": the value is explicitly stated in the text, table, or figure.
  - "paper_inferred": the value was deduced from context (e.g., Qiskit usage implies simulator if no QPU is named; D-Wave implies quantum_annealer).
  - If you infer a value, you MUST add an explanation to provenance.notes (e.g., "hardware.type inferred as simulator_statevector because paper uses Qiskit with no QPU device named").
  - If a field cannot be reported or inferred, set it to null — do NOT guess.
- Return ONLY the JSON object.
